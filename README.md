# llm-lab

Small, reproducible measurements of local language models, run on ordinary hardware.
Each folder is one experiment, with the script, how to run it, and the raw results.

## truncation

Does Ollama silently cut the start of a long prompt? A 5,488-token prompt with a rule at the top,
100 synthetic client notes (18 late deliveries) and a question at the end, run with Ollama's default
context and with `num_ctx 32768`.

```bash
cd truncation
node truncation-test.mjs llama3.2:3b 3   # model, runs per configuration
```

Requirements: Node.js 18+ and Ollama running on `http://localhost:11434` (override with
`OLLAMA_URL`). The script installs nothing and changes no Ollama setting; it unloads the model after
each run so cached prompts cannot distort the timings. Results go to `truncation/results/`.

`results/2026-10-17T11-40-30-078Z.json`: Intel i7-8665U, 32 GB RAM, no GPU, Ollama 0.40.5,
`llama3.2:3b`. Its default-configuration runs 2 and 3 show 0.2 s reading times: they reused a cached
prompt (fixed since); only run 1 timing is valid.

## speed

Can you predict how fast a model will write before downloading it? The rule of thumb says
`tokens/s ≈ memory bandwidth ÷ weights read per token`. The script prints that prediction next to
the measured speed for every installed model, including a mixture-of-experts model (`gpt-oss:20b`),
which reads only part of its weights per token.

```bash
cd speed
node speed-test.mjs 3                          # 3 runs per model, every installed model
node speed-test.mjs 3 llama3.2:3b gpt-oss:20b  # or a chosen list
```

The default bandwidth (38.4 GB/s) is the theoretical figure for dual-channel DDR4-2400; set
`BANDWIDTH_GBS` for your machine. Close other heavy programs first: a download running in the
background slowed the first smoke test (`results/smoke/`). Results go to `speed/results/`.

## task

Does a model hold on a real task, run after run? The same 100 synthetic notes as `truncation`, two
tasks: count the clients who complained about a late delivery (18), then list them all. Because the
data is synthetic, the script knows the right answer and scores every run itself: no LLM judge.

```bash
cd task
node task-test.mjs 10                          # 10 runs per task, every installed model
node task-test.mjs 10 llama3.1:8b              # or a chosen list
```

It uses `num_ctx 8192` so the 5,463-token prompt is never cut, and each model's default temperature
with a different seed per run. Every raw answer is saved in `task/results/`.

## notes

The `task` test, split into small questions. Instead of reading the 100 notes at once, the model
gets one note at a time and a yes/no question ("does this note say the client complained about a
late delivery?"); the code counts the "yes" answers and lists the clients. Same data, same scoring.
One run = 100 short calls, timed end to end.

```bash
cd notes
node note-test.mjs 10                          # 10 runs, the 4 small models of the task test
node note-test.mjs 10 llama3.1:8b              # or a chosen list
```

Each wrong or unclear answer is kept raw, with the wording of the note, in `notes/results/`.
`results/smoke/`: one run of `llama3.2:1b` (it answered "no" to all 100 notes).

## context

What does a bigger context cost in memory, and what does a second user cost in waiting time? Part 1
loads the model with `num_ctx` 2048 to 32768, with the KV cache in f16 (default) then `q8_0`, and
reads the memory used. Part 2 sends 1, 2, 3, then 4 requests at the same second, with
`OLLAMA_NUM_PARALLEL` at 1 (default) then 2, and times the wait before each answer starts.

```bash
cd context
node context-test.mjs 3                        # 3 runs of part 2, llama3.2:3b
node context-test.mjs 3 llama3.1:8b            # or another model
```

The script starts its own Ollama server on port 11500 for each configuration (the settings are
environment variables, so they need a server restart) and stops it afterwards; your Ollama on 11434
is left alone. Each server log is saved with the results: it shows the command Ollama gives its
engine (`-c` context, `-np` parallel slots, `--cache-type-k`) and the engine's memory breakdown.
`results/smoke/`: one run of `llama3.2:1b`.

Method inspired by the "Kit IA locale" masterclass on local AI agents
([video](https://www.youtube.com/watch?v=MNFZoZUExSQ)).

## gateway

Can a token gate in front of Ollama give each person their own access, without slowing anything
down? Caddy 2.11.7 runs in Docker in front of the Ollama on this PC, with one token per person
(`users.caddy`, generated by the script and never committed). The script checks that no token and a
wrong token are refused, that each person gets in, that a valid token still cannot delete, pull or
create models (only chat, generate, embed, list and the `/v1` API go through), that a token can be revoked with a reload (no
restart), that the access log names the person but never shows the token, the delay the gate adds,
and whether streaming still streams.

```bash
cd gateway
node gateway-test.mjs               # llama3.2:1b
node gateway-test.mjs llama3.2:3b   # or another model
```

Requirements: Docker running, Ollama on `http://localhost:11434`. The gate listens on
`127.0.0.1:8088` only, and the script stops it at the end.

`results/2026-10-27T13-47-59.328Z.json`: Intel i7-8665U, 32 GB RAM, no GPU, Windows 11 + Docker
Desktop, Ollama 0.40.11, `llama3.2:1b`. 11/11 checks; +2.6 ms per call (median of 50); first
streamed chunk 84 ms direct, 91 ms through the gate. Ollama itself has no guard: a delete request
for a model that does not exist reaches it and gets 404, so a real name would be deleted. The admin
checks use that missing name, so the test never deletes or downloads anything. One thing seen: a connection whose last answer was a
refusal (401) is cut when Caddy reloads, so the client's next request on it fails once with a
socket error. Connections that last served a normal answer are not affected.
